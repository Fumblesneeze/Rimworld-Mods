## Context

Thin Walls is a new RimWorld 1.6 product mod owned exclusively by **Thin Walls** (`fumblesneeze.thinwalls`) at `mods/ThinWalls`. The installed design target is RimWorld `1.6.4871 rev590`; the inspected `Assembly-CSharp.dll` SHA-256 is `5CF1B5BE399D5B1C9C56CA72C9D35B4ECF307FEACF5859D04AC5A1AA5926356A`.

Vanilla RimWorld represents walkability, edifices, rooms, and construction footprints primarily per cell. A thin wall instead occupies one undirected cardinal edge between two cells. Either adjacent cell/side pair may describe that edge during designation, but there is only one physical placement slot. Up to four differently oriented segments may coexist with a pawn or ordinary building on one cell when they occupy four different shared edges.

RimWorld 1.6's Burst-compiled `PathFinderJob` already consumes a `NativeArray<CellConnection>` containing eight directional connection bits per cell. This is the stable engine seam for an edge blocker; transpiling the Burst job or pretending an edge wall is an impassable cell would either be unreliable or violate the core free-cell requirement.

The product requires Harmony because placement, path-job parameterization, immediate reachability, stale-path execution, construction wiping, and frame rendering have no complete XML/public extension surface. The product never references or ships the Dev Gateway. The Gateway and dynamically staged tests are verification tools only.

## Goals / Non-Goals

**Goals:**

- Expose one Stuff-selecting Structure designator that places straight cardinal runs and derives their owned edge from the right-hand side of the drag vector.
- Preserve one segment's identity, hit points, damage, cancellation, construction, deconstruction, and save/load on each unique undirected collision edge.
- Keep the owning cell standable and otherwise available for floors, zones, items, pawns, one-cell buildings, and compatible portions of multi-cell buildings.
- Prevent native player placement of any building footprint whose internal cell adjacency crosses a completed, blueprinted, or framed thin-wall edge.
- Remove blocked cardinal and endpoint-crossing diagonal connections from normal pawn path jobs, reject stale crossings at movement execution, and let destroyable-traversal jobs attack the encountered segment rather than pass through it.
- Render Core-derived narrow Stuff-tinted edge structures as visibly continuous straight, L, T, and + unions plus square west/east/north/south regular-wall end and side contacts, without diagonal width transitions.
- Add edge-mounted Thin Doors that leave both adjacent cells free, use ordinary RimWorld door access/opening delays, and open only for a path step that crosses their owned edge.
- Split vanilla regions and rooms at completed Thin Wall and Thin Door edges so room identity, room stats, roles, and temperature containment match the visible boundary.
- Explicitly provide no roof support and no automatic roof area.
- Produce reproducible, player-facing About/Workshop art and descriptions plus native in-game evidence for the reviewed package.

**Non-Goals:**

- Replacing, patching out, or changing vanilla walls, doors, fences, or columns.
- Diagonal or curved edge segments, adjustable thickness, powered Thin Doors, automatic conversion of existing walls, or optional-mod integrations.
- Treating Thin Walls as cover, projectile interception, line-of-sight, animal-pen, gas, wind, light, or vacuum boundaries. Room identity, room statistics, roles, and temperature are included; those unrelated systems require their own explicit edge-aware contracts.
- Making thin walls support roofs.
- Publishing or mutating a Steam Workshop item. This change prepares reviewed publishing inputs only.

## Decisions

### 1. Use owned cardinal designations and unique canonical shared-edge keys

The domain model uses `OwnedEdge(cell, side)` where `side` is North, East, South, or West. `SharedEdge` canonicalizes the two adjacent cells plus axis, so `(cell, North)` and `(cell + North, South)` address the same placement, collision, rendering, room, and save identity.

Up to four `OwnedEdge` values may exist at one cell when their `SharedEdge` values differ. Placement rejects any completed building, blueprint, frame, or pending constructible phase whose `SharedEdge` equals the candidate, including the opposite owner description from the adjacent cell. Direction reversal may select the same physical edge but cannot create a second Thing.

Alternative considered: allow two Things to own opposite descriptions of the same edge. Rejected by the user's 2026-08-18 designation reference because the duplicate produces ambiguous construction and malformed rendering. Legacy/corrupt doubled data may be handled defensively, but the player workflow never creates it and no product visual depends on it.

### 2. Combine a rotatable click preview with right-hand multi-cell drag orientation

`Designator_ThinWall` is a parameterless special Structure designator backed by `TW_ThinWall`; the Def disables its default `Designator_Build`. A Thin-Walls-owned `DrawStyleCategoryDef` exposes only the vanilla cardinal `Line` worker. Outside a multi-cell drag, `placingRot` is the authoritative single-cell orientation and ordinary Q/E designator rotation cycles it through the four edges; ghost and highlight rendering use it directly. Mouse-down does not change it while the drag remains on one cell.

Once the drag contains a second distinct cell, the designator reads the drag origin/current endpoint, chooses the dominant cardinal axis exactly as `DrawStyle_Line` does, and maps the vector's right side as follows:

| Drag direction | Owned edge |
| --- | --- |
| East | South |
| North | East |
| West | North |
| South | West |

A newly selected tool defaults to South. A single click uses the Q/E-selected edge. Multi-cell right-hand orientation may become the next hover orientation after release, but pointer jitter inside the start cell or returning to that cell cannot overwrite an explicitly selected click edge. Drag previews draw the actual edge structures rather than full-cell ghosts.

Alternative considered: four separate build commands. Rejected because one rotatable click preview provides the same control while preserving the requested origin-to-destination rule for lines. Arbitrary angled lines are rejected because one constant cell-edge side cannot represent them without discontinuous or ambiguous stair steps.

### 3. Represent every phase with ordinary constructible Things

`TW_ThinWall` is a Stuff-made, standable, non-edifice `Building_ThinWall` with explicit `holdsRoof=false`, `allowAutoroof=false`, zero path cost, no floor coverage, and zone coexistence. The base wall comparison is Core `Wall`: cost `5`, base maximum hit points `300`. Thin Walls uses ceiling-half material cost `3` and base maximum hit points `150`; Stuff factors apply normally to both.

Blueprints use `Blueprint_ThinWall` and retain edge rotation. Frames remain vanilla `Frame` Things and are recognized through `entityDefToBuild`. All phases therefore use RimWorld's native resource delivery, construction work, cancellation, failure, damage, deconstruction, selection, and Scribe persistence. The derived map index is rebuilt from spawned Things and is never an independently serialized source of truth.

Alternative considered: serialize edge records only in a `MapComponent`. Rejected because it would require recreating construction, damage, selection, ownership, save compatibility, and resource refunds outside native gameplay.

### 4. Make placement edge-aware while preserving cell coexistence

A prefix on `GenConstruct.CanPlaceBlueprintAt_NewTemp` first applies a pure `ThinWallPlacementRules` check:

- thin-wall placement rejects an out-of-bounds opposite cell, an exact owned-edge duplicate, or a completed/planned/in-progress crossing footprint;
- ordinary building placement rejects any internal cardinal adjacency of its rotated occupied rectangle that has a completed, blueprinted, or framed thin wall;
- overlap checks ignore thin-wall phases after the edge-crossing check passes, so even a one-cell full building may use the owner cell exactly as it could use an otherwise free cell.

`GenSpawn.SpawningWipes` is forced false between thin-wall constructible phases and otherwise compatible Things so blueprint-to-frame-to-building transitions never erase another orientation, a floor, or a co-located building. Construction blocking is guarded by the same public placement rules, and shared-edge uniqueness prevents an opposite-owner phase from being created.

Alternative considered: four invisible attachment buildings. Rejected because vanilla attachments still inherit cell placement/wiping assumptions and cannot validate arbitrary multi-cell footprint crossings.

### 5. Overlay vanilla path connectivity before Burst jobs are scheduled

`ThinWallMapComponent` maintains a `NativeArray<CellConnection>` with the same length as the map's vanilla connectivity. A postfix on `PathFinderMapData.GatherData` rebuilds the overlay only after vanilla data sources finish and only when path data changed. The rebuild copies vanilla connectivity, then removes:

- both directions of the cardinal connection crossing each completed shared edge; and
- both directions of the four diagonal pairs whose center-to-center segment intersects either endpoint of that wall edge.

Inclusive endpoint blocking prevents diagonal corner slipping through a wall endpoint or an L/T/+ junction; pawns can still walk around an exposed endpoint by taking cardinal cells around it.

A postfix on `PathFinderMapData.ParameterizePathJob` supplies the overlay to normal path jobs. Only a request that explicitly permits door bashing receives vanilla connectivity so its bash path can reach the wall; hostile identity alone and a generic destroyable traversal request without executing bash permission remain edge-blocked. The overlay is updated only at the pathfinder's gather/scheduling boundary, avoiding mutation while Burst jobs may be reading an earlier array. A wall change dirties both adjacent path cells and invalidates edge-reachability labels.

Alternative considered: transpile `PathFinderJob.Execute`. Rejected because the installed job is Burst-compiled and a Harmony-managed IL patch is not a reliable native-job contract. Alternative considered: mark the owner cell impassable. Rejected because it violates pawn/building coexistence.

### 6. Guard reachability and movement execution

Vanilla region reachability can produce false positives because it is cell/region based. A postfix on `Reachability.CanReach` refines an accepted answer through a reusable edge-aware subregion graph: cells are component-labeled inside each vanilla Region, Thin Wall edges split those components, and query traversal still calls `Region.Allows` with the complete `TraverseParms`. Only explicitly bash-capable traversal remains allowed through a segment. A deliberate Thin Door room split can instead make vanilla return false for an authorized crossing. That one case is recovered only after the edge graph accepts and an exact-request native `FindPathNow` returns a real path that actually crosses a concrete Thin Door. An exact-request re-entrancy scope admits only the path request's nested validation; tick-, pathing-revision-, complete-`TraverseParms`-, and door-access-scoped caches prevent the recovery from promoting unrelated vanilla failures or rebuilding the full graph for every repeated query.

`ReachabilityImmediate.CanReachImmediate` rejects Touch adjacency when every relevant step crosses a thin wall. Prefixes on `Pawn_PathFollower.SetupMoveIntoNextCell` and `TryEnterNextPathCell` reject stale normal paths before tweening or changing `Pawn.Position`. A pawn whose active job explicitly permits door bashing plans through destroyable traversal and receives an edge-aware blocker job against the concrete `Building_ThinWall` Thing when it reaches the edge. That job invokes the pawn's ordinary RimWorld melee verb and damage while remaining on its current side; it does not directly mutate wall hit points.

Alternative considered: rely only on the pathfinder overlay. Rejected because already-issued paths, immediate Touch checks, and cached region answers can otherwise cross or act through a newly completed segment.

### 7. Compile one Core-derived linked silhouette for every local topology

The rejected renderer treated every wall strip as an independent raster and tried to hide its endpoint with posts, stitches, caps, and diagonal perspective ramps. That architecture cannot produce the same visual grammar as RimWorld's linked walls: internal outlines survive, coplanar overlays fight for depth, north-south pieces look pasted onto horizontal pieces, and a regular-wall contact reads as a decal rather than one wall. Those assets, recipes, connector variants, renderer paths, screenshots, and publishing cards are invalidated. They are not reference art for the replacement.

The replacement is a custom linked renderer with a grid-corner topology contract. At each integer grid corner it records four incident edge rays in stable north/east/south/west order and the four adjacent ordinary-wall quadrants. Each edge ray is `None`, `Thin`, or `Ordinary`; an occupied ordinary-wall quadrant identifies the corresponding 30-by-30 quadrant of the concrete resolved 60-by-60 Core atlas tile, including its actual alpha, top, face, side, and outline pixels. It is not approximated as an opaque floor square. The renderer also retains Thin Wall versus Thin Door identity, material, damage, and phase. The directional ray table has `3^4 = 81` combinations before ordinary quadrant, door, and damage state. A pure `HybridWallTopologyCompiler` SHALL enumerate them without choosing one preferred bridge ray or dropping an incident arm.

The compiler returns one alpha-coherent sprite-space union plan per grid corner and one replacement-tile plan for every affected regular wall. Each plan has one exterior silhouette, one dark outline around only that silhouette, ordered top/front/side regions, material ownership, one narrow union shadow, and owner-clipped damage regions. The analytic top union is completed first; visible front/side faces and the contour are derived only from its final exterior boundary. A ray-local endpoint cannot survive inside a collinear or perpendicular union, a horizontal endpoint cannot grow a longitudinal side slab beyond its requested vertex, and a north-going arm joined to either horizontal arm loses its complete 28-by-22 south-facing terminal facade because that vertex is no longer exposed. Collinear, L, T, and + forms are linked atlas states, not collections of endpoint sprites. There is no junction post, endpoint cap, collinear stitch, longitudinal construction contour, free-standing connector decal, single-ray bridge selection, coplanar arm stack, miter, wedge, or chamfer. Thin-only junctions remain constant-width axis-aligned unions. A mixed Thin-to-regular contact is a square butt union: the regular wall's ordinary-width linked arm reaches its native tile perimeter and the constant-width Thin arm begins outside it. Every structural pixel is assigned once before printing.

The three user-supplied drawings retained under `references/` are normative geometry inputs. Forward/reverse shared-edge identity, non-contact offset examples, exact square end/corner contacts, and side-T contacts apply in every rotation and reflection.

The visual source is the installed RimWorld 1.6 Core wall material, sampled at runtime and never copied into the package. The pinned 1.6.4871 Core atlases are 320×320, arranged as the exact vanilla 4×4 `LinkDirections` table. Each 80×80 atlas slot has a ten-pixel gutter on every side and `MaterialAtlasPool` exposes its inner 60×60 sample with scale `0.1875` and offsets `(column × 0.25 + 1/32, row × 0.25 + 1/32)`. The exact horizontal `East|West` sample has two north-outline rows, a 33-row dark top plane at rows 2–34, a 22-row three-course front face at rows 35–56, and a three-row antialiased/south outline at rows 57–59. The exact north-south `North|South` sample has a three-column west outline at columns 0–2, an eleven-column lit west side at 3–13, a 33-column dark top plane at 14–46, a ten-column lit east side at 47–56, and a three-column east outline at 57–59. Bricks, Planks, and Smooth share those structural boundaries. In Bricks, the measured top/front luminance ratio is `107.92/228.88 = 0.472`; the vertical top/mean-side ratio is `109.41/173.09 = 0.632`. These values, source hashes, atlas index order, and extraction identity are recorded without redistributing Core pixels. The compositor admits only those exact three named atlases with their pinned RGBA hashes. A mod atlas that merely happens to be 320×320 cannot be assumed to share Core's slot semantics and therefore keeps its native renderer.

Thin geometry narrows only the wall footprint/top plane; it never scales the complete sprite or shortens a visible wall face. In the Core inner-tile coordinate system, a horizontal Thin arm is exactly a seven-row top plate plus the complete 22-row, three-course south face and its Core-equivalent north/south contour. A north-south Thin arm is exactly a seven-column top plate plus the complete eleven-column west and ten-column east visible sides and their Core-equivalent contours. At an exposed south-facing end of a north-south arm, the 22-row three-course facade spans the complete projected side envelope—not only the seven top pixels—so an endpoint covers columns `16..43` while its top remains `27..33`. This is the narrowed counterpart of Core's vertical endpoint perspective, not a needle, post, or cap. Those bands are positioned in the same sprite-space projection as the source atlas; they are not treated as literal upright 3D faces, rotated between orientations, or flattened into ground ribbons. The compiler builds the final alpha silhouette from axis-aligned top-footprint rectangles, derives faces from only the final exterior boundaries, and maps the matching Core top/front/side UV bands onto those surfaces. Surface ownership remains causal: a west/east side cap extruded from a horizontal arm remains horizontal-owned even inside a mixed junction and never receives north-south-only material remapping. This preserves the Core fixed-camera perspective and the deliberately darker top at every zoom.

The final boundary-balanced runtime tile uses Unity's south-west-origin 60-by-60 inner-tile coordinates. A horizontal straight has top rows `38..44` and front rows `16..37`; a north-south straight has top columns `27..33`, west-side columns `16..26`, and east-side columns `34..43`. A north-only endpoint has its exposed south facade at rows `8..29` across the complete envelope columns `16..43`. Two solid-dark exterior pixels and one antialias ring are derived after the surfaces are unioned. Directional endpoints, L, T, and + states are produced by adding ray rectangles to that same raster and extruding faces only from final exposed south/west/east boundaries. There is no independently transformed arm texture.

The later integral `+8` horizontal balancing transform cannot be allowed to disconnect a south-going arm from that translated top band. In every Thin-only L/T/+ containing South plus at least one non-door East/West wall, the same seven-pixel north-south structure therefore continues from row `30` through the final horizontal top before faces are derived. The non-door horizontal foreground owns and visibly reclassifies the complete seven-pixel bridge at rows `31..37` as front face; only rows `38..44` remain visible as top behind it. A door-only horizontal contact is deliberately narrower: because no horizontal wall facade exists, only the incident door's three fixed-frame pixels continue through rows `31..37` as top and the rest of the South width stays absent. Doubled South ownership never widens that fixed frame. When a non-door wall and an opposing door coexist, the wall's complete foreground facade bridge wins.

The inverse North case begins with a real exposed-end facade at rows `8..29` plus its top/side projection through row `37`, so the complete terminal projection is clipped rather than bridged. As soon as any horizontal wall or door participates in the vertex, every North-owned pixel in the complete projected envelope across rows `8..37` is removed first; no unoccupied screen-space half may survive as a pasted endpoint slab or doubled overlap square. Each incident wall half then replaces rows `16..37` with its horizontal facade. A door half restores only its three fixed-frame columns as horizontal facade while its moving-leaf aperture remains empty. The continuing North member begins where it meets the horizontal top at row `38`. Standard and doubled North widths derive the removed envelope from the same top-plus-side depths, and a wall beats a door at their shared center column. These junction-only corrections create neither a post nor a cap; they prevent the terrain notch caused by disconnected masks, the bright rectangular top tab caused by retaining an internal endpoint, and the full-width slab that would fill a moving door aperture.

The source bands above define shape and perspective but do not, by themselves, define where the finished plane is placed relative to the two adjacent cells. Placement uses the complete final structural-alpha envelope after top/front/side union and exterior-contour derivation. Along the segment's normal axis, the shared grid boundary is mapped to the midpoint of that envelope, with at most one source pixel of imbalance. Thus a horizontal edge balances its complete visible body between the north and south cells even though its lit facade lies on one side of its dark top in source UV space; a north-south edge balances the complete west/top/east envelope between the west and east cells. The derived normal translation is shared by ghost, blueprint, frame, completed wall, door frame/leaf, selection, and damage. Sun shadows are excluded because their cast direction changes with the celestial vector, but their `7/60` physical base is itself centered on the edge. Collision, pathing, room, and building-crossing semantics continue to use the unmodified canonical shared edge.

The measured final straight bounds make that transform concrete. Including the two solid outline pixels and one antialias ring, the horizontal body initially occupies source rows `5..39`, whose pixel-edge extent `[5,40]` has midpoint `22.5`. The integral 60-pixel compiler translates horizontal structural/contour samples eight rows, producing final extent `[13,48]` around boundary coordinate `30`: seventeen pixels on one side and eighteen on the other. This is the closest raster representation of the ideal 7.5-pixel correction and satisfies the one-pixel invariant. The north-south body occupies columns `13..46`, whose edge extent `[13,47]` already has midpoint `30`, so its X correction is zero. Render planes remain centered on canonical grid edges/vertices; balance is compiled into the one linked raster instead of moving north-south endpoints longitudinally. Horizontal hybrid gutters and their apertures receive the same eight-row raster transform inside the single `120x120` composition before its five disjoint crops are submitted; no shifted connector plane is introduced. The versioned runtime key and coordinate contract are recorded in `references/2026-08-19-core-derived-atlas-and-adjacent-building-plan.md`.

Compatible adjacent buildings receive a separate render-only clearance measured against their actual direction-specific final nonzero-alpha silhouette and the complete finished Thin-wall silhouette. A completed ordinary building, its blueprint, and its frame first inspect only Thin Wall/Thin Door structures on the exterior perimeter of their final occupied rectangle; if none exists, no graphic/material resolution or GPU alpha readback occurs. The current Thing/style graphic and its native print-versus-realtime path are authoritative: rotated cached printing uses the native `180`-degree flip angle without UV mirroring, realtime rotated drawing additionally uses the flipped mesh UVs, non-rotated cached printing uses `GraphicData.flipExtraRotation`, and non-rotated realtime drawing does not. The corresponding plane-size swap or mesh rotation, `Graphic.DrawOffset`, and phase are included. The Core Hand Tailoring Bench north/south completed/blueprint texture remains pinned at a `224x96` canvas with alpha bound `[16,16,208,89)`, but the two sides use the wall-facing half of that resolved projected sprite rather than splitting its total 73-row alpha depth symmetrically. Its Core Frame instead uses the actual always-present `1.15x` footprint underfield/corner envelope and therefore measures `23/60` on either north/south side; reusing the completed bench's `27/60` silhouette for the Frame is forbidden. An attachment Frame also includes vanilla's half-cell draw translation along its rotation vector. Unmeasurable/custom-UV graphics fail closed without moving or throwing. The prior `22/60` rule is superseded because its promoted live crop visibly hid part of the north workbench. Each side is displaced by the smallest `1/60`-quantized amount that leaves a one-source-pixel safety band between final opaque/antialias silhouettes; excess displacement is also a failure. Contributions are deduplicated by side, signed side-specific components combine, and perpendicular contacts compose. Regular walls, ordinary doors, Thin structures, and non-buildings are excluded. Realtime draw and cached map-mesh graphic/shadow centers use the same offset. Position, occupied cells, interaction cells, pathing, reservations, rooms, jobs, bills, and save state remain exact vanilla values. Successful measurements are cached by actual graphic/texture/rotation/native-draw-path/flip/flip-angle/draw-size/draw-offset/attachment-offset/phase, Thing identity, and a dedicated Thin-edge visual revision so an edge lifecycle, style, or phase change invalidates it without invalidation from unrelated ordinary buildings, doors, terrain, or path-cost activity.

Every horizontal Thin top/facade samples the measured Core `East|West` straight donor. Every south-visible endpoint facade samples that same three-course `East|West` facade donor. This remains true inside L/T/+ unions. Non-straight Core atlas slots donate ordinary-wall quadrants only: their interior fill, end bevels, and turn highlights may never leak into a Thin arm. No image-generation model, prompt, generated candidate, or generated source is permitted for Thin Walls, Thin Doors, damage, icons, previews, title art, or Workshop cards. Disposable generated concept sheets may be used only to elicit human geometry feedback under ignored artifacts; each accepted/rejected observation must be transcribed into the normative requirements matrix before another iteration, and no pixels or style from those sheets may influence runtime or publishing output.

When a Thin arm reaches the exact perimeter of a completed Core or compatible standard linked `building.isWall` tile, the affected regular wall SHALL NOT first print its unchanged atlas tile and then receive a connector decal. The renderer resolves the concrete wall's ordinary link index and material, reads the installed tile into a transient runtime buffer, and emits one padded hybrid replacement composition. The hybrid is built like a square mixed-width Core linked state, not like a connector. The same structural/contour mask applies to diffuse and Stuff mask. Multiple exact contacts union before exterior contour derivation; proximity without incidence contributes nothing.

The hybrid texture is exactly `120x120`; its centered `60x60` native region begins as a byte-for-byte copy of the original diffuse and Stuff-mask tile while its gutter begins transparent. The semantic aperture is declared before mutation from any simple-contact outgoing arm or side-T narrow contour replacement, constant-width outer bands, square shoulders, and their antialias neighborhoods. Every original byte outside that aperture remains identical before material resolution. A simple contact selects preserved ordinary body plus straight-donor ordinary arm material; a side-T selects the preserved native straight body plus only the regular-material structural replacement of its seven-pixel contour contact; both then add Thin-family straight-donor samples in the gutter and one exterior outline. Mixed Stuff participants may be resolved into one neutral cutout raster. After composition only, sampling partitions the result into native and exterior layers with disjoint visible alpha; this is not a structural overlay or independent connector. Multiple legal apertures are unioned in one pass and printed once at native Building altitude. A diagonal miter, clipped face/side, independent wedge, collar, stretched chamfer, transparent contact slit, or overlapping continuation is forbidden. Unsupported wall atlases and missing required straight-donor bytes fail closed to native printing. Removing the last incident Thin structure restores the exact native `Graphic_Linked` path.

Installed Core pixels may exist only in transient runtime textures keyed by the native material, ordinary link index, exact Thin contact descriptors, owner widths/sides, family, damage, and door state; they are never serialized or packaged. The runtime tile is compiled as one linked raster and split only into disjoint native/exterior sampling geometry after all topology, material, damage, and contour decisions. For mixed Stuff contacts, participant diffuse/mask/color inputs are resolved before composition rather than trying to force incompatible per-participant uniforms through one final material. Damage is applied to the selected Thin owner's structural pixels before the exterior contour is finalized; no structural top, face, side, outline, jamb, or connector is a separate coplanar decal.

Shadows use RimWorld's native sun-shadow mesh/material contract instead of a dark translated copy. The completed Thin topology at a vertex compiles one height-`1.0` `SunShadowFade` base from the union of centered `1 × 7/60` horizontal and `7/60 × 1` north-south half-rays. Base runs and casting edges are extracted from that final union; vertex intersections are owned once, canvas/raster handoff boundaries never cast, and an endpoint occupied by another ray cannot emit a ray-local shadow edge. Closed Thin Doors use the same full footprint; opening leaves move two half-length volumes. An affected regular wall suppresses its native rectangular shadow and compiles one custom mesh from the final native-region top mask. A simple contact may add its ordinary arm and square shoulder; a side-T retains the native straight top footprint and meets the exclusively Thin-owned gutter at the narrow boundary. Raster cells map at `1/60` world cell and exterior shadow edges remain axis-aligned. Directional cast-shadow pixels are excluded from the structural boundary-balance metric.

Damage is deterministic and attached to the compiled geometry. Moderate, heavy, and severe variants are constructed from versioned line/chip/fiber/dent primitives or runtime Core damage materials, then clipped to the affected Thing's actual face/top polygons before printing. A moderate one-cell sample has a coherent face/side defect at least eight source pixels long and three across with at least twelve recess and four highlight/chip pixels. Heavy retains it, adds a separated defect and a top-plane defect, and changes at least `1.6` times as many structural pixels. Severe also clears at least two adjacent diffuse/mask structural pixels and surrounds the void with material-specific recess/highlight treatment. Stone uses branching cracks and irregular chipped brick/mortar clusters, wood uses offset tears and long splinters without plus-sign silhouettes, and metal uses asymmetric depressions, displaced plate edges, and one-sided highlights rather than ring symbols. The three grades must be orderable at ordinary zoom, with heavy/severe still distinct at far useful zoom. At a junction or regular-wall aperture, clipping happens after topology composition so damage cannot float beside the wall or cross the perpendicular mixed-material boundary.

`Blueprint_ThinWall`, the narrow `Frame.DrawAt` Harmony path, the custom designator, `Building_ThinWall`, `Building_ThinDoor`, and affected regular-wall printing use this one compiler. Focused tests enumerate every directional state and reject disconnected masks, internal endpoint outlines, duplicate coplanar polygons, non-manifold overlaps, omitted rays, full-sprite scaling, and changes outside a regular-wall aperture.

Alternative considered: retain the rejected strip sprites and improve their posts/ramps. Rejected because local correction cannot turn independently outlined rasters into one linked silhouette. Alternative considered: package transformed Core atlas pixels. Rejected because the same result can be derived from installed Core materials at runtime without redistributing base-game art.

### 8. Put Thin Doors on the edge while reusing vanilla door behavior

`TW_ThinDoor` is a Stuff-made `Building_ThinDoor` derived from `Building_Door`, but remains standable and non-edifice so both adjacent cells stay ordinary map cells. It uses the same right-hand cardinal line contract as Thin Walls, costs ceiling-half of the Core simple door (`ceil(25 / 2) = 13` Stuff), and has half its base durability (`160 / 2 = 80`). A shared edge contains at most one Thin Wall or Thin Door constructible phase.

The pathfinder keeps Thin Wall edges closed. A Thin Door edge is available to a pawn that can open that concrete door or while the door has free passage, closed to a pawn that cannot open it, and available to an explicitly bash-capable request so the concrete door can be attacked. Request-specific door access is applied to an isolated connectivity snapshot whose lifetime extends through the scheduled Burst job; no array is mutated while a job can read it. A postfix on `Pawn_PathFollower.NextCellDoorToWaitForOrManuallyOpen` returns the concrete edge door only when the pawn's next cardinal step crosses it. Vanilla then performs its ordinary manual-open wait and stance. Movement entry still checks the exact edge, so walking within either adjacent tile is unaffected and a stale path cannot cross a closed inaccessible door.

The Thin Door is another typed Thin ray in the linked topology. Its Def uses `MapMeshAndRealTime`: cached-map `Print` emits the fixed endpoint union even when the door is the canonical lowest-ID owner at a shared vertex, while realtime drawing emits only the moving leaves. The closed leaf and fixed frame are first compiled as one semantic top/front/side union. Longitudinal leaf caps are suppressed where they meet the fixed three-pixel frame, and one exterior contour is derived around frame plus leaf; separate capped slabs are forbidden. Every closed leaf surface retains its source texture/material details but receives a deterministic `0.84` panel tone before the center seam and family-specific marks, keeping the door distinct from floors and terrain at ordinary zoom. The fixed endpoint frame receives neither the panel tone nor the door seam and remains source-equivalent linked wall material. At a regular contact, the padded cached replacement contains the native-region square shoulder and only the three fixed frame pixels at the grid vertex; the other twenty-seven pixels of that regular-owned half-edge remain absent because they belong to the moving leaf. Each realtime leaf excludes exactly those three fixed longitudinal source pixels: the closed left leaf covers `[-0.45,0]` with U `0.05..0.5`, the closed right leaf covers `[0,0.45]` with U `0.5..0.95`, and the two leaves still meet as one continuous central union. Thus the cached fixed frames plus the realtime leaf partition the full edge without a gap or coplanar overlap. At `OpenPct <= 0.05` the two closed leaves are emitted as one continuous trimmed union plane so no UV-slice transparency can create a false central passage. Above that threshold, vanilla `OpenPct` moves two semantic leaf halves longitudinally toward the endpoints; only the newly exposed inner leaf ends receive a contour, while the frame-contact ends remain uncapped. Travel is capped at `0.30` cell: the fully open physical plan is `[-0.75,-0.30]` and `[0.30,0.75]`, but realtime draw and shadow intervals are clipped to the framed aperture, submitting only `[-0.45,-0.30]` with U `0.35..0.5` and `[0.30,0.45]` with U `0.5..0.65`. This leaves a centered `0.60` passage while one real `0.15` panel-toned leaf panel and its paired latch marks remain visibly identifiable at each jamb; the previously accepted `0.10` tips failed the context-free ordinary-zoom review as hairlines. The fixed frame remains the nonmoving part of the same compiled silhouette; it is not a jamb sprite, raised post, cap, or overlay. In the fully closed phase the leaf is `0.004` altitude units above the completed Thin Building-layer wall plane. A Thin-owned fixed frame is exactly another `0.002` above that leaf. A regular-owned fixed frame remains part of the native hybrid regular-wall plane and needs no artificial raised layer because its three-pixel interval is spatially disjoint from the trimmed leaf. Door planes are never based on RimWorld's lower `DoorMoveable` layer, because that camera-projects an edge door away from its wall. Moving leaves preserve the Core-derived CutoutComplex shader, Stuff mask, textures, and colors and override only the material render queue to the realtime transparent queue so a cached map-mesh quad cannot hide them; replacing that shader with a mask-incompatible transparent shader is forbidden. When open, the surrounding linked arms and frame retain one continuous exterior outline, the unsubmitted outer leaf portions are mechanically retracted behind the frames, and the two visible inner panels bound a genuine collision-independent `0.60` passage with no cached wall face, damage, center-cell art, second overlay, or hanging half-cell leaf slab. Its blueprint, frame, owner-clipped damage, shadows, hold-open command, save/load state, and ordinary melee destruction remain visible on the same edge geometry. It never supports or requests a roof.

Every closed material family receives the same small paired latch marks on the actual visible moving-leaf faces: a dark mount with one warm exposed highlight, clipped and moved with each leaf. Ordinary Thin Walls and fixed frames never receive it. Leaf surfaces use a measured `0.84` panel tone: enough contrast to distinguish the door from its wall, but not the rejected `0.72` near-black slab that loses the source material. The fixed endpoint raster is clipped after every face pass, not only while building its top mask. Thin-only endpoints keep the three-pixel horizontal top plus lateral facade or the three-pixel north-south top plus lateral sides. A regular-owned endpoint keeps only the three-pixel gutter top because the connected ordinary square shoulder and body already form its jamb; adding another facade/side would create the hanging block rejected in live review. A longitudinal end cap, south-facing endpoint facade, or foreground repaint may not expand either form into the moving leaf span or a half-cell slab. The closed leaf remains `0.004` above the completed Thin wall surface, and a Thin-owned fixed frame remains `0.006` above that surface. Once the leaves separate, their moving planes instead use `AltitudeLayer.Building - 0.001`, measured from the raw native Building altitude rather than from the completed Thin-wall offset. They are therefore below both native regular walls and completed Thin walls. Regular-owned frames remain in the native hybrid plane; Thin-owned frames keep their fixed raised altitude. The translated leaf is clipped to `[-0.45,0.45]` before submission, with UVs clipped by the same length, so altitude ordering is never used to hide geometry beyond the frames. Its shadow unions that clipped leaf with the adjacent fixed-frame span, which is excluded from the regular hybrid shadow and therefore cast once. The visible opening therefore never contains a hanging half-leaf block while standalone doors still visibly slide along their edge.

Sparse cached endpoint-frame diffuse and Stuff-mask textures disable mipmaps. A three-pixel frame otherwise collapses into the lowest mip levels of its transparent one-cell plane and produces a ghosted Core wall footprint around a standalone door. Sampling is resolved per emitted partition: adjoining full Thin Wall partitions, union outlines, and moving leaves retain normal Core-derived mipmaps while only sparse door-frame partitions disable them. Door shadows are native realtime `SunShadowFade` meshes and have no raster texture or mipmap policy.

For every `OpenPct` from zero through `0.05`, the realtime geometry uses the canonical zero-open bounds and UVs; the animation threshold never slides, stretches, or overlaps either fixed frame. The fully closed realtime shadow still covers the complete one-cell edge because it is the combined leaf-plus-frame structural volume. When regular-contact ownership removes a door ray from the Thin vertex, that removed ray cannot select Thin-frame altitude for an unrelated retained wall partition.

Alternative considered: place an invisible vanilla door edifice in one adjacent cell. Rejected because it would make every approach to that cell pay door behavior, prevent compatible buildings there, and violate the free-cell requirement.

### 9. Split vanilla regions at completed edge boundaries

Completed Thin Walls and Thin Doors are room boundaries even though their Things are non-edifices. The product replaces only `RegionMaker.TryGenerateRegionFrom` when a map contains completed Thin edge structures, reproducing RimWorld 1.6's region construction while adding one rule: the cardinal flood and generated `RegionLink` spans may not cross an occupied completed edge. The implementation preserves the expected `RegionType`, one-cell portal handling for actual vanilla doors, extents, map-edge flags, link canonicalization, and region lister registration. Maps without completed Thin edge structures remain on the unmodified vanilla method.

Spawning, completing, despawning, destroying, deconstructing, and loading a Thin Wall or Thin Door dirties both incident vanilla regions before the next room rebuild. A closed or open Thin Door remains a room divider, matching vanilla door portals; its inherited temperature tick is redirected to exchange heat only between the two rooms immediately across its owned edge, at vanilla simple-door open/closed rates. Thus enclosed cells report an indoor room, room roles/stats are scoped correctly, and temperature does not leak through a Thin Wall. Thin edge structures still contribute zero roof support and do not seed automatic roofing.

Alternative considered: maintain a parallel mod-only room database and patch individual room consumers. Rejected because it would miss Core and modded systems that consume `Room`, `District`, room roles, or temperature trackers.

### 10. Keep release art non-generative, reproducible, and separate from acceptance evidence

The mod owns a 1280×720 title master, a deterministically derived 640×360 `About/Preview.png`, and wide 1164×655 Workshop cards below 1 MiB. Source manifests bind copy, alt text, dimensions, local font, exact accepted in-game capture hashes, and output hashes. Every pictured wall or door is an exact crop from the accepted minimized Gateway run. Typography, labels, arrows, comparison layout, and the no-roof symbol may be deterministic vector/raster overlays, but neither generated imagery nor a reconstructed wall/door diagram is permitted. The title master must also be composed from accepted in-game renders and deterministic typography rather than generated concept art. Cards show the actual edge geometry and benefits they claim; they do not use unresolved Steam URLs.

The complete in-game acceptance sessions remain under ignored evidence. Eight reviewed captures from the accepted minimized Gateway run are explicitly promoted into the tracked Workshop source tree with their original screenshot names, run identity, visibility/minimized state, and byte hashes. Promotion happens only after live and independent visual acceptance, so the cards consume evidence without becoming the evidence. The furnished-room captures follow the accepted realistic-base design record; the catalog/junction captures remain clearly labeled in-game technical comparisons.

## Risks / Trade-offs

- **[Risk] Another pathfinding mod replaces the same `ParameterizePathJob` or connectivity lifecycle.** → Use narrow postfixes, exact signature/startup ownership tests, no private copies of optional assemblies, one bounded compatibility warning, and fail closed at movement execution.
- **[Risk] Copying the full connectivity byte grid after a path-data change adds main-thread work.** → Rebuild only when `GatherData` reports a change, use one byte per cell plus an edge iteration, retain allocation-free buffers, and benchmark a large-map wall catalog in the live process.
- **[Risk] Edge room boundaries require a narrow replacement of vanilla region generation.** → Shape-test the exact installed method and fields, reproduce the current algorithm line-for-line with only the edge predicate added, bypass the patch on maps without completed Thin edge structures, and prove native room IDs, stats, temperatures, spawn/despawn rebuilds, vanilla doors, and ordinary no-Thin-Wall maps in isolated RimWorld processes.
- **[Risk] Thin Door access differs per pawn while the Burst pathfinder consumes immutable connectivity.** → Reuse the shared wall snapshot when possible and allocate a bounded request-specific snapshot only when concrete door access differs; retain it through job completion and dispose it in the exact pathfinder lifecycle.
- **[Risk] A segment constructed after path gathering leaves one tick of stale connectivity.** → Dirty path data immediately and enforce both setup and final-entry movement guards; the next gather publishes the new overlay safely.
- **[Risk] Multiple selectable Things in one cell can make a particular segment harder to click.** → Move each segment's draw/selection center to its edge, use narrow orientation-specific draw size, retain vanilla selection cycling, and verify deconstruction of each orientation through the native UI.
- **[Risk] A deterministic hybrid mesh can still reproduce the wrong projection or retain hidden atlas outlines.** → Pin the exact Core atlas bands and hashes, test all 81 typed-arm states and every aperture rotation, compare source UV regions and output silhouettes mechanically, then inspect the complete linked-topology catalog at close, ordinary, and far useful zoom in RimWorld.
- **[Risk] Room sealing could be mistaken for every regular-wall system.** → Publishing and inspect text name room/temperature integration and explicitly exclude roof support, cover, projectile, sight, pen, gas, wind, light, and vacuum behavior unless later specified.

## Migration Plan

1. Add the new package and test projects without changing Immersive Chefs or the Dev Gateway package boundary.
2. Build repository-local output, then deploy only `fumblesneeze.thinwalls` for intentional isolated runs.
3. Launch every verification process with a unique `-savedatafolder`, dedicated log, exact PID/start identity, and Harmony/Core/Thin-Walls order; append Gateway only for gateway-assisted evidence.
4. Hash the user's normal `ModsConfig.xml` before and after. No workflow writes it; if an existing repository launcher temporarily stages a package, its exact marker-owned stage is removed in guaranteed cleanup.
5. Rollback is removal/disablement of the new package. No vanilla Def, save, Workshop directory, or other mod file is edited. Saves without the mod lose Thin Walls Things through RimWorld's ordinary missing-Def behavior; uninstall recovery is not claimed.
