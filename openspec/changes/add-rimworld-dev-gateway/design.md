## Context

Desktop automation can prove that RimWorld reached a menu, but Unity exposes little useful UI Automation state and game-specific setup remains slow and brittle. The gateway therefore runs inside RimWorld, where it can observe game state, evaluate raw C# through bundled Mono.CSharp, and marshal commands to Unity's main thread. Direct HTTP is the normal interactive path; an optional companion host tool remains useful for process launch, newer-language assembly compilation, repeated HTTP calls, and evidence collection.

This is deliberately a separate mod: **RimWorld Dev Gateway** (`fumblesneeze.rimworlddevgateway`, `mods/RimWorldDevGateway`). Immersive Chefs and other product mods must remain loadable, buildable, and releasable without it. The gateway is an unrestricted development instrument, not a security boundary suitable for a normal colony or a remotely reachable host.

The target development environment is RimWorld 1.6 on Windows, .NET Framework-compatible mod assemblies, and the repository's Zlepper build/test framework. Unity lifecycle, initialized Defs, maps, rendering, input, Mono.CSharp evaluation, and optional uploaded code execution require in-game verification even when contracts are covered by fast tests.

## Goals / Non-Goals

**Goals:**

- Start a discoverable, authenticated, loopback-only, versioned HTTP API whenever the mod is loaded.
- Provide structured state, logs, screenshots, raw input, semantic actions, unrestricted stateful raw-C# execution, optional uploaded-assembly execution, and named automations without restarting RimWorld to extend a test.
- Provide stable semantic control and inspection for ordinary verification work: developer/god modes, time, camera, map/view things, selections, debug actions, spawning, gizmos, targeting, placement, and drag designations.
- Marshal all Unity/RimWorld state access onto a durable main-thread dispatcher and return correlated, bounded JSON success/error envelopes.
- Make repeatable quickstart scenarios cheap enough to become the normal in-game verification path.
- Leave prominent, redundant evidence that the dangerous developer-only gateway is active.

**Non-Goals:**

- Remote access, LAN binding, TLS termination, multi-user authorization, sandboxing, code signing, or making arbitrary execution safe for an untrusted caller.
- Shipping the gateway as an Immersive Chefs dependency or exposing gateway types from a gameplay mod.
- A complete declarative language for every RimWorld action; raw in-process C# is the intentional escape hatch when named automation and semantic actions are insufficient.
- Persisting gateway state into saves or promising that a save mutated by arbitrary development code remains valid.
- Bundling Roslyn, the host .NET SDK, or a modern CoreCLR compiler service into Unity; the deliberately small Mono.CSharp evaluator is part of the gateway runtime.

## Decisions

### 1. Pinned EmbedIO owns the loopback HTTP transport

The mod will host its API with **EmbedIO 3.5.2**, using the package's managed .NET Standard 2.0 assets, and will bind the resulting `WebServer` explicitly to `http://127.0.0.1:<port>/`. It will never accept a configured bind address other than IPv4 loopback. The default port is dynamically selected; an optional preferred port may be tried before falling back to another loopback port. EmbedIO owns HTTP parsing, connection lifecycle, request contexts, routing, and response writes. Gateway code owns authentication, API envelopes, endpoint-specific body and response limits, concurrency, timeouts, and main-thread dispatch. The gateway will not maintain a parallel hand-written `TcpListener` or raw HTTP parser.

Kestrel is not a viable in-process server for this mod. Current Kestrel is part of ASP.NET Core and expects the `Microsoft.AspNetCore.App` shared framework and a modern .NET/CoreCLR host. RimWorld 1.6 loads mod assemblies into Unity's Mono, .NET Framework-compatible AppDomain, which does not supply that shared framework. Copying a subset of Kestrel assemblies into a mod would not recreate its supported runtime and would introduce a large, runtime-sensitive dependency set.

Watson.Lite also provides a .NET Standard 2.0 path, but its package graph adds both `Watson.Core` and `CavemanTcp` as direct runtime dependencies. EmbedIO 3.5.2 has one direct runtime package dependency, `Unosquare.Swan.Lite` 3.1.0, and explicitly supports Mono/.NET Framework. On this repository's `net48` mod target, that resolves to `Swan.Lite.dll` plus its small `System.ValueTuple` 4.5.0 compatibility assembly. The smaller pinned graph reduces the number of assemblies Unity must resolve and the chance of collisions with other mods, while still avoiding a bespoke protocol implementation.

The distributable gateway package must therefore contain the compatible `EmbedIO.dll`, `Swan.Lite.dll`, and `System.ValueTuple.dll` next to the gateway assemblies. The execution path additionally packages the .NET Framework asset from Mono.CSharp 4.0.0.143 as `Mono.CSharp.dll`. A successful normal .NET test run is not sufficient evidence: the minimal Core-plus-gateway in-game smoke must prove that RimWorld's actual Unity Mono host loads all four DLLs, starts the loopback server, evaluates raw C#, serves authenticated requests, and shuts down without `FileNotFoundException`, `TypeLoadException`, `MissingMethodException`, compiler-initialization, or assembly-resolution errors. Unrestricted execution remains enabled by default and is not gated by this transport choice.

All public routes are rooted at `/api/v1`; an unsupported `/api/vN` returns a structured `unsupported_api_version` error and the supported version. The initial routes are:

### 2. Every run gets an unlogged bearer token and manifest

On successful bind, the mod creates a cryptographically random 256-bit bearer token and a run ID. It atomically writes a session manifest beneath the active RimWorld save-data folder, under `DevGateway/Sessions/<run-id>/session.json`, plus an atomically replaced `DevGateway/current.json` locator. The manifest includes API version, loopback base URL, token, PID, process start identity, run ID, game/mod versions, timestamps, and the development-only warning. The same run directory receives a token-free `requests.jsonl` and atomically replaced `last-request.json` containing request ID, method, path, phase, timings, and terminal HTTP/error data. While any requests remain active, `last-request.json` identifies the newest admitted active request in `started` state; when none remain active, it contains the most recently recorded terminal request. An older completion therefore cannot hide a newer hang, and a newer quick completion cannot hide an older request that is still in flight. The token is never written to the RimWorld log, request journal, or an API error.

Every route, including status and shutdown, requires `Authorization: Bearer <token>`. Token comparisons are constant-time. Requests from a non-loopback peer are rejected even though the listener itself is loopback-bound. Shutdown removes the token-bearing current manifest and replaces the run manifest with a stopped tombstone that contains no credential. The session manager classifies exact Windows sharing/lock failures without sleeping and retains its claim. The persistent Unity host retries once per rendered frame for a short bounded window, then throttles attempts while retaining ownership until cleanup succeeds; it never destroys the host or permits an overlapping restart merely because the fast window elapsed. At startup, stale manifests whose PID/start identity no longer matches a live process are made credential-free.

The alternatives of a fixed secret, no authentication, or per-request confirmation were rejected. A generated token limits accidental cross-process access without adding friction to autonomous tooling. It does not make unrestricted execution safe against another process running as the same user, and the warnings state that plainly.

### 3. Network work and game work are separated by a main-thread dispatcher

Network workers only parse, authenticate, validate limits, create a request context, and await a dispatcher result. The EmbedIO request cancellation signal is linked into queued and cooperative work so a disconnected caller cannot leave an unstarted mutation behind. A persistent Unity component created after long-event initialization drains a bounded FIFO dispatcher queue during `Update` and supports end-of-frame work for screenshots. Each queued command carries a request ID, enqueue time, deadline, cancellation state, and operation name.

Queue admission, queue wait, and response wait have bounded configurable ceilings. A command whose deadline elapsed before it starts is skipped. Results and errors use one envelope:

```json
{
  "apiVersion": "1",
  "requestId": "caller-or-generated-id",
  "ok": true,
  "durationMs": 12,
  "result": {}
}
```

Errors set `ok` to `false` and replace `result` with `{ "code", "message", "details", "retryable" }`, using stable codes and appropriate HTTP status. A caller-supplied `X-Request-Id` is accepted after length/character validation; otherwise the server generates one. Exception details are bounded, logged with the same ID, and included for this development-only API.

Once unrestricted code begins synchronously on the main thread, .NET cannot safely preempt it. The HTTP waiter can time out and cooperative execution context cancellation is signaled, but malicious or hung code can still freeze the game. This inherent trade-off is surfaced by status, documentation, and tests rather than hidden behind a false sandbox promise.

### 4. Observability uses snapshots and cursor-based logs

Status and UI-state DTOs are immutable snapshots assembled on the main thread; network threads never walk live Verse or Unity objects. Version-one status contains only `developerOnly`, nullable `map`, `pendingDispatches`, `processId`, `programState`, `rootType`, nullable `tick`, `unrestrictedExecutionEnabled`, and `warning`; a map contains `Handle`, `Biome`, `Width`, and `Height`. Version-one UI state contains only `programState`, `rootType`, up to 256 selection entries with `Handle`/`Label`, and up to 128 window entries with `Handle`/`Type`/`Modal`.

Versions, pause/speed, view/input geometry, action descriptors, upload counts, and operation/automation health are deliberately not implied by those DTOs. Callers use the session manifest and dedicated discovery endpoints for their defined data, or inspect unknown state through raw C# or a named automation. Promoting another field into a stable snapshot requires a later OpenSpec/API change.

The gateway subscribes to Unity log callbacks and captures gateway/RimWorld messages into a 2,000-entry sequence-numbered ring buffer. Each entry includes sequence, UTC time, severity, a bounded message and optional stack trace, thread identity, and request ID when emitted during a gateway operation. Reads clamp to 500 entries and a 3 MiB serialized `Entries` budget. `HistoryEvicted` reports a cursor gap; `PageTruncated` separately reports that more matching retained entries remain beyond the active count or byte bound. A caller resumes a truncated read after the final returned entry sequence, not the ring-wide newest cursor.

Screenshot capture is queued for end-of-frame, encodes PNG, and returns bytes with request/capture metadata headers. A JSON metadata/result form may return a manifest path instead when explicitly requested, but base64 image data is not placed in normal status responses. Captures enforce size and timeout limits and destroy temporary textures.

### 5. Raw input is process-scoped; semantic actions are preferred for known controls

Raw click, drag, key-chord, and text operations use client-pixel coordinates relative to the current RimWorld window and validate that the target window belongs to the current PID immediately before injection. On Windows the implementation may use narrowly wrapped `user32` input APIs, bringing the RimWorld window to the foreground when requested and returning its actual client rectangle/DPI transform. Minimized, missing, mismatched, or out-of-bounds targets fail explicitly. Drag duration and interpolation steps are bounded.

These process-scoped Win32 calls do not inspect or mutate live Verse/Unity objects. Click, drag, key-chord, and text injection all run on request workers and share one cancellation-aware input lane per gateway runtime, so global `SendInput` sequences cannot interleave. In particular, the timed drag interpolation loop runs outside Unity's main thread, allowing RimWorld to render and process each injected event. Client disconnect or server-shutdown cancellation interrupts queued input and timed waits; cleanup retains the lane until any injected button, key, modifier, or Unicode-down event has received its best-effort release. Unity/RimWorld state capture and semantic mutations still use the dispatcher.

Raw input is useful for unknown mod UIs but can be focus-sensitive. Registered semantic actions therefore invoke known RimWorld operations directly on the main thread and publish name, description, availability, and argument schema through `GET /api/v1/actions`, independently of the narrow UI-state DTO. They include common pause/speed/window cancel/confirm actions plus `debug.tool.cancel`, which clears only an active native `DebugTools.curTool`. They can be extended without changing the API version. A semantic action does not pretend to be a pixel click; its result records the resolved action and state change. Version one reports unsupported native input through explicit request errors rather than status geometry/backend fields.

Cross-platform native input backends are deferred. Uploaded main-thread code and semantic actions remain available when a platform lacks a raw-input backend.

### 6. Semantic game control uses stable handles and native game APIs

The broad semantic surface is split into four cohesive services behind the existing main-thread dispatcher: game/camera state, thing queries and inspection, developer tools/spawning, and gizmos/interactions. Network code only validates bounded request DTOs and serializes immutable results. Verse adapters resolve and mutate live objects exclusively on the Unity thread.

`GET /api/v1/game-state` remains the dedicated expanded control snapshot. It reports `Prefs.DevMode`, `DebugSettings.godMode`, pause/speed, current map handle, camera center/native zoom/view rectangle when a map is visible, and the current bounded selection. The narrower `/ui-state` deliberately duplicates only effective pause/native speed and rendered-client coordinate bounds because those are necessary to drive and observe screen-local input. `POST /api/v1/game-state` applies only supplied fields after validating the complete transition. Enabling god mode requires developer mode already enabled or enabled in the same request; disabling developer mode also disables god mode. Time-speed names use the native `Paused`, `Normal`, `Fast`, `Superfast`, and `Ultrafast` values. Camera changes are absolute and map-scoped so retries do not accumulate pan/zoom drift.

Thing handles use a spawned `Thing`'s stable-in-run `ThingID`; map handles remain `map-<uniqueID>`. A query is limited to the current map and either all spawned map things or things whose occupied rectangle intersects the current camera view. Results sort by handle and paginate with an exclusive `after` handle, so callers never receive an unbounded object graph. Filters cover exact Def names, coarse thing kinds, exact runtime type names, faction relation/name, label substring, fog state, and selected state. Inspection returns bounded scalar identity, position, stack, faction, hit-point, quality, forbidden/selection, inspect-string, component-type, and pawn-specific summaries; it never recursively serializes `Thing`, `Pawn`, `Map`, `Hediff`, `Job`, or component objects. Selection changes resolve and validate every requested handle before changing the selector.

Native debug-action discovery walks only RimWorld's already-materialized generated tree breadth-first and returns handles derived from full path, node/delegate source identity, category, allowed game state, and action mode. It never evaluates lazy `childGetter` submenus during discovery; those potentially enormous generated menus are exposed as unsupported, while each throwing mod descriptor getter is isolated and recorded. Invocation re-resolves the handle and rejects stale or ambiguous nodes. Immediate nodes run directly, with completion meaning the delegate returned even if it opened a dialog. RimWorld's generic `ToolMap`, `ToolMapForPawns`, and `ToolWorld` leaves do not expose a coordinate callback: `DebugActionNode.Enter` installs a `DebugTool` whose closure later reads `UI.MouseCell()` or `GenWorld.MouseTile()` during a native pointer event. The gateway therefore activates that exact native tool and returns a bounded `pointerRequired` result; the caller applies it with the existing process-scoped raw click and can clear it with `debug.tool.cancel`. It does not pretend to pass a cell that the native API does not accept. Known operations may gain typed adapters separately. The dedicated spawn endpoint is exactly the version-one `quickstart.spawn` alias for bounded center-relative building/item/pawn entries: it resolves all named Defs, Stuff, PawnKindDefs, qualities, counts, resulting cells, and placement feasibility before the first mutation, then uses native generation/spawn APIs and returns handles plus a mutation ledger. A caller-supplied idempotency key prevents duplicate spawn sets after an HTTP retry.

Gizmo discovery accepts selected things, explicit thing handles, or architect categories. It enumerates current `Gizmo`/`Command` instances and resolved `Designator`s without retaining them across maps, bounds the result, and reports owner, label/description, disabled reason, hotkey, group key, toggle state when observable, and one interaction kind: `immediate`, `toggle`, `target`, `placement`, `drag`, or `unsupported`. A handle includes the map/owner, source, runtime type, stable ordering key, and a query revision. Invocation re-enumerates and fingerprints the candidate before use; a stale handle fails without invoking a different command.

Immediate and toggle commands finish in their invocation response. Target commands and designators create at most one active semantic interaction. The returned interaction declares its accepted input shapes plus its map, owner, and revision fingerprint. Applying it accepts exactly one matching input: a thing handle, map cell, explicit bounded cell set, line, or rectangle. The gateway resolves shapes deterministically, removes duplicate cells, preflights every target through the native targeting/designation validator, and then invokes the native callback or designator. It reports accepted/rejected cells and completion state. A new interaction is rejected while another is active unless the caller cancels the exact handle; map changes, destroyed owners, or changed gizmo fingerprints make the handle stale. Native debug tools instead activate RimWorld's own pointer tool and use the process-scoped input route because their closures read current UI coordinates. No endpoint synthesizes `Event.current` or silently falls back to pixel input. World targeting, mod-defined multi-stage interactions, and custom GUI-only gizmos remain explicitly unsupported until a typed adapter exists.

This semantic protocol is intentionally not a universal serializer or a promise to parameterize every mod-defined command. Unsupported custom gizmos/debug tools return their concrete runtime type and reason; the always-on raw C# endpoint remains the escape hatch and can be used to prototype a later typed adapter without restarting the game.

### 7. A stateful raw-C# REPL is the primary always-on escape hatch

Unrestricted execution is enabled whenever this mod is running, including its default configuration. It has no restart-required switch, allowlist, signature check, per-call confirmation, or dependency on a predeclared automation. A caller needs only the current per-run bearer token and can use HTTP directly; no companion client is required.

`POST /api/v1/executions/csharp` accepts the submission itself as the request body. The media type must be `text/plain`, optionally with `charset=utf-8`; another media type or charset is rejected before dispatch, malformed UTF-8 is rejected rather than replacement-decoded, and an optional UTF-8 BOM is stripped. The endpoint caps source at 65,536 encoded bytes, and the evaluator defensively caps it at 65,536 decoded characters. Diagnostics are capped at 16,384 characters, result text at 65,536 characters, and runtime type text at 1,024 characters. The normal JSON envelope returns an evaluation record with `Succeeded`, `ResultSet`, invariant-culture `Value` text when present, runtime `Type`, and bounded `Diagnostics`. A compilation error or incomplete submission is a completed evaluation (`ok: true`, `Succeeded: false`) rather than a transport failure. Source, media, decoding, initialization, dispatch, or runtime failures use stable structured gateway errors.

The mod packages the .NET Framework asset from Mono.CSharp 4.0.0.143 and owns one evaluator for the gateway run. It references the gateway, loaded RimWorld, Verse, Unity, framework, and compatible optional-mod assemblies and preloads common namespaces. Submissions are serialized and evaluated through the main-thread dispatcher. Successful declarations, variables, methods, and `using` directives remain available to later submissions in that run, so this behaves as a REPL rather than a stateless one-shot compiler. There is deliberately no per-request or unauthenticated reset switch in version one: controlled gateway shutdown or RimWorld process teardown discards the evaluator, and a fresh gateway process starts with clean evaluator state.

Mono.CSharp is intentionally smaller and better matched to Unity Mono than current Roslyn/Kestrel-era runtime stacks, but it does not promise the latest host SDK language version. For code needing newer C# syntax, complex project references, or a precompiled reusable probe, `POST /api/v1/executions/assembly` remains an optional fallback. It accepts a size-bounded compiled assembly payload and exact public-static entry contract, loads it into the current AppDomain, and invokes it through the same main-thread dispatcher. Uploaded code may use reflection or direct references to loaded assemblies and may register session-scoped actions or automations.

The optional companion host command creates a temporary .NET Framework-compatible project, references the local RimWorld/Unity managed assemblies plus the gateway contract assembly, uses the installed host .NET SDK compiler to produce a uniquely named DLL, uploads it, and deletes its temporary build directory. Roslyn is not shipped in the mod. Assembly unload is impossible in the default AppDomain, so this fallback enforces a 16 MiB limit on each upload and reports a monotonic upload count. It deliberately has no rate or hard per-run total that would force a restart; ordinary exploratory work should prefer the stateful raw endpoint, which does not load a new assembly per submission.

### 8. Automations are registered, discoverable synchronous workflows

An automation registry publishes stable names, descriptions, versions, argument schemas, prerequisites, and current availability. `POST /api/v1/automations/{name}/runs` dispatches the handler to the main thread and waits for it, returning a terminal `succeeded`, `failed`, `cancelled`, or `timed-out` run with bounded completed progress/artifacts, timings, result or error, and mutation data. The registry may internally pass through queued/running/cancel-requested states and retain cooperative cancellation hooks, but version one has no remote list-runs, get-run, incremental progress polling/streaming, or cancellation endpoint. Those lifecycle APIs require a future OpenSpec/API change. Duplicate caller idempotency keys return the existing terminal run rather than spawning the scenario twice.

The first built-in flow is `quickstart.spawn`. Its version-one descriptor requires `version: 1`, accepts an optional `center: { x, z }` and `clearRadius`, and accepts bounded `buildings`, `items`, `pawns`, `research`, and `gameConditions` arrays. Building entries use `defName`, optional `stuff`, `count`, `quality`, `offset: { x, z }`, and `powerOn`; item entries use the same shape without `powerOn`; pawn entries use `kindDefName`, `count`, and `offset`; research accepts a Def name string or `{ defName }`; and a game condition uses `defName` plus `durationTicks`. Version one caps each section at 64 entries, total spawned buildings/pawns at 256, an item entry at 5,000 units, a pawn entry at 32 pawns, offsets at 64 cells per axis, clearing at radius 20, and a condition at 3,600,000 ticks.

The host launcher may start RimWorld with an isolated save-data folder, `-quicktest`, and an ordered minimal list of Core, zero or more explicitly supplied additional package IDs, and the gateway. After the gateway manifest appears and a playable current map is ready, the automation resolves every supplied Def, Stuff, quality, cell, and other feasible prerequisite before mutation. It uses deterministic radial placement, clears only a bounded non-pawn area when requested, configures requested power state, completes research, registers conditions, centers the camera, and returns resolved Defs, spawned stable handles, positions, warnings, and a mutation ledger. Unknown properties, invalid Defs, impossible cells, or unsatisfied map prerequisites fail before feasible mutation.

The host smoke captures an initial log cursor before setup. After the terminal quickstart run and idempotent replay it records fresh `post-quickstart-status.json`, `post-quickstart-ui-state.json`, and a bounded `post-quickstart-logs.json` page after that cursor, then captures the visible scene. The authenticated Gateway end-of-frame PNG is the mandatory exact-process visual artifact. FlaUI desktop/window capture is redundant: its bounded failure is retained in `flaui-evidence.json` and may not abort later input/cleanup when the Gateway PNG already exists, but it remains fatal when no mandatory PNG exists and is never replaced with a relabeled copy. Each FlaUI subprocess has a host timeout and is terminated only through its retained process handle; an unconfirmed termination is a fatal ownership failure. Service and connection intent is persisted in memory before invocation, then cleanup reconciles observed disconnected/stopped state after uncertain responses while preserving a service that was already running and disconnected. This separates startup observations from evidence of the mutated scenario while retaining explicit page-truncation semantics.

Scenario descriptors live outside the save and may be repository files consumed by the host tool. Product mods can provide descriptors without referencing the gateway assembly. Custom behavior beyond the declarative schema is handled by an uploaded assembly, which can then be promoted into a named automation only when reuse justifies it.

### 9. Isolation and warnings are part of the product contract

The About metadata labels the mod as developer-only and dangerous. A startup warning, status field, session manifest warning, settings/about text, and visible main-menu indicator state that any local bearer-token holder can execute unrestricted code as the RimWorld process. The API never offers a non-loopback setting.

Host smoke/quickstart tooling uses an isolated `-savedatafolder` and isolated `ModsConfig.xml` containing only required official/core mods, the target product mod(s), and the gateway. If a future tool must touch the normal `ModsConfig.xml`, it must hash and back it up first, restore it in `finally`, and verify the restored hash. The current design does not require modifying the user's normal configuration.

Optional-mod behavior is resolved by package ID or Def name at runtime. The gateway and its built-in automations have no compile-time reference to Immersive Chefs or optional Workshop assemblies.

### 10. Finalized Def export is bounded JSON, not reconstructed canonical XML

RimWorld 1.6 exposes `GenDefDatabase.AllDefTypesWithDatabases()` and `GetAllDefsInDatabaseForDef(Type)`, so the Gateway can enumerate the actual objects remaining after XML inheritance, conditional loading, PatchOperations, parsing, cross-reference resolution, and Def post-processing. `POST /api/v1/defs/export` therefore filters and snapshots those live databases on the dispatcher instead of implementing a second Def loader.

The snapshot sorts by fully qualified database type and ordinal `defName`, accepts an exact top-level `fieldNames` selector, and carries the retained `modContentPack` and `fileName` provenance separately. Paging uses two independently canonical Base64-encoded strict-UTF-8 identity segments in a versioned cursor, so embedded newlines cannot corrupt the boundary; non-reversible live identities are omitted with a warning. Page-count candidates are bounded before projection. Exact serialized-byte/node pagination may project the next boundary candidate to measure it, but omits that candidate and returns the last accepted exclusive cursor if the complete success envelope would exceed 32 MiB or 500,000 JSON nodes.

The field walker reads fields only, skips static and `[Unsaved]` members, represents nested Defs as typed name references, detects reference cycles, and enforces fixed depth, node, 1,024-entry collection, 65,536-character runtime-string, 512-projectable-field, 4,096-total-reflected-member, 1-MiB-complete-field-entry, 8-MiB-complete-Def, 500,000-node/32-MiB-envelope, page, 1,024-database-type-candidate, and 100,000-Def-source-candidate bounds. Reflected-member accounting occurs before exclusions; the one residual non-preemptible operation is the CLR/Mono runtime's synchronous `GetFields` call that returns each declared-member array. A wide object retains named field-limit markers or the largest deterministic sorted field prefix rather than collapsing into a useless whole-object marker. Actual JSON serialization measures keys, values, metadata, warnings, cursor, and envelope overhead, including worst-case escaping and structural node expansion. These values are Gateway payload/work policy, not limits imposed by EmbedIO, Zlepper, Unity, or RimWorld.

The field limit is grounded in a local RimWorld 1.6 inventory: the Core `ThingDef` inheritance chain exposes 276 reflected fields and 253 projectable fields after static/`[Unsaved]` exclusions, so 512 leaves about two-times headroom. The byte and response-node values are intentionally tunable developer-tool policy rather than discovered engine maxima: a 32 MiB/500,000-node Def page reserves half of the Gateway's 64 MiB transport-response ceiling while bounding structurally dense dictionary/list snapshots, with 8 MiB per item and 1 MiB per selected root field so ordinary patch-authoring exports are not forced into tiny fragments. The unrelated 4 MiB integration-snapshot bound is justified by that endpoint's fixed 64-assembly/128-result/64-failure cardinalities and bounded strings; it is not a general HTTP or Def-export ceiling.

Cancellation is polled through source scans and supported collection/field projection. Only cancellation associated with the active request token escapes; a mod-thrown unrelated `OperationCanceledException` is isolated. Warning text records a safe runtime exception-type marker without calling arbitrary virtual `Message` or `ToString`, and type text is read only from the known CLR/Mono runtime `Type` implementation. Per-field/per-Def failures become warnings so one unusual mod object cannot take down the export or the game.

RimWorld also exposes `DirectXmlSaver`, but it is not the inverse of the Def loading pipeline. The unified patched `XmlDocument` is local to `LoadedModManager.LoadAllActiveMods` and is discarded after parsing. `DirectXmlSaver` instead walks public and non-public runtime fields, deliberately omits `[Unsaved]` fields such as source provenance, may expand direct Def/object references, and has no cycle, node, byte, cancellation, or HTTP-safe failure boundary. Its reconstructed output can contain post-load runtime state that was never legal source XML. Version one consequently returns explicit JSON snapshot metadata and rejects XML format requests rather than calling this serializer and mislabeling its output as canonical patched XML.

### 11. In-game integration tests are separately staged and startup-gated

Zlepper.RimWorld.ModSdk.Testing 0.0.9 configures a normal NUnit/VSTest host and RimWorld assembly references only. Its assembly contains no types and its MSBuild targets provide no game process, Def loader, lifecycle hook, test discovery, or in-game executor. It remains the correct host-unit-test SDK, but the Gateway owns the missing real-game runner.

`RimWorldDevGateway.IntegrationTesting` is a small host-safe shared contract. Public static parameterless `void` methods carry `[IntegrationTest(RunAt.MainMenuLoaded)]` or `[IntegrationTest(RunAt.PlayableMapLoaded)]` and signal failure by throwing, normally through the supplied assertion helpers. No NUnit engine is shipped into Unity. Reflection discovery is sufficient for this contract, so version one does not add a source generator.

Test projects opt in with `RimWorldInGameIntegrationTest=true`, declare one owning package ID, and carry a bounded `*.integrationtests.json` manifest naming the one sibling `*.IntegrationTests.dll`. A reusable manifest may provide required/forbidden package constraints; a product-specific matrix instead uses `activePackageSetMode: "exact"` plus a nonempty ordered `activePackageIds` value and cannot mix it with nonempty constraints. Manifest properties are closed and unique. Host tooling requires the complete nonempty ordered active package sequence on every invocation, discovers and builds only matching opted-in projects against the exact selected RimWorld/Workshop paths, then places the DLL and validated manifest in marker-owned repository test-mod roots. Missing input has no build-all fallback. Exact mode compares count and ordinal position with case-insensitive package identity before build, repeats that check against the built manifest before staging, and repeats it in game against the actual active `ModContentPack` order before any assembly load source is exposed. The isolated launcher copies bundles below each owning mod's version-resolved `DevIntegrationTests` folder and removes only its exact owned stages. The test DLLs are absent from ordinary product packages. The game never starts a compiler: with `-devGatewayRunIntegrationTests`, the Gateway scans only active mods through their resolved load folders, validates that each manifest owner matches its containing mod, loads only the named traversal-safe DLL bytes with bounded same-directory dependency resolution, requires exact normalized assembly name/version/culture/public-key-token identity, and records manifest/assembly/discovery failures independently.

Discovery is an update-driven state machine. Cursor admission stays incremental, while one background task at a time performs an admitted source's byte load and all `GetTypes`/`GetMethods`/`CustomAttributeData` work under hard 64-attempt, 128-test, 64-failure, 256-type-per-assembly, 128-method-per-type, and 8,192-work-step limits. Failed loads consume the attempt limit. The Unity update loop only polls task completion and never waits for an incomplete task; invocation alone returns to Unity. A stuck mod reflection worker therefore cannot freeze a rendered frame, but cannot be safely aborted either, so process replacement is the cancellation boundary.

Endpoint and artifact use the same immutable snapshot and 4 MiB aggregate serialization ceiling. A single background persistence lane serializes and atomically writes attachment, running, and terminal candidates. Publication occurs only after durable commit and keeps the exact candidate object; `GET /integration-tests` returns retryable 503 before initial attachment and the last committed object thereafter. A transient failure retains and retries that same candidate and gates discovery/invocation/advancement instead of inventing a terminal infrastructure result or rerunning a test. Exception formatting calls no arbitrary virtual exception text: exact trusted assertion/standard types may contribute separately bounded `Message` and `StackTrace`, while all other types receive a fixed suppression marker. Raw components are truncated before redaction or concatenation.

The persistent runtime host observes settled native lifecycle conditions each frame, checking Unity-thread ownership before consulting lifecycle probes. It fires the main-menu point only after play data is loaded, no long event is active or waiting, the entry root/UI root/window stack exist, and that complete condition survives into the next rendered frame; `ExecuteWhenFinished` alone is too early because it runs before RimWorld's later interface-initialization action. The playable-map point requires `ProgramState.Playing` plus a current map. Tests run synchronously on the Unity thread once per point and process, in deterministic order. Each invocation is exception-isolated and timed; it is not falsely advertised as preemptible. Async-void tests are rejected through metadata inspection because their completion cannot be observed; Task-returning tests remain outside the version-one contract. A fresh isolated RimWorld process is the only supported suite reset because loaded assemblies, Def databases, Harmony owners, worker cancellation, and other engine statics cannot be reliably returned to a pristine state.

These tests are the honest place to assert final Def values, XML patch effects, optional-mod shapes, or `Harmony.GetPatchInfo` results across selected mod lists. They remain supporting integration evidence. A player-visible mod feature still requires the repository acceptance gate's native player action and observed behavior.

## Risks / Trade-offs

- **[Unrestricted local code execution]** → Bind only to loopback, generate a per-run bearer token, never log it, show redundant danger warnings, and keep the gateway out of gameplay dependency graphs. This reduces accidental exposure but intentionally does not sandbox trusted development code.
- **[Raw or uploaded code can freeze, corrupt, exit, or delete through the RimWorld process]** → Document the capability honestly, use isolated save data for automated runs, provide cooperative cancellation/deadlines, and treat each verification run as disposable.
- **[A stateful REPL can retain surprising declarations or mutations]** → Serialize submissions, identify the run in every response, document that state lasts for the process, and use controlled shutdown/restart as the version-one reset boundary.
- **[Mono.CSharp accepts an older language surface than the host SDK]** → Keep the common direct-HTTP path dependency-light and retain optional host-compiled assembly upload for newer syntax or complex project references.
- **[A timed-out main-thread call may still finish later]** → Skip expired queued work, distinguish `timed_out_before_start` from `response_timeout_after_start`, carry cancellation, observe and request-correlate every late success/fault with its full internal stack, and use idempotency keys for mutating automations.
- **[Several valid requests can stall one rendered frame]** → Execute at most one admitted Unity operation per dispatcher phase/frame; one inherently expensive operation can still consume its own frame and is diagnosed by elapsed time and the request journal.
- **[A blocked Unity thread cannot answer its own health endpoint]** → The host records its request before transmission, classifies an exited process separately from a live timed-out process, asks the exact owned window to close, captures a Windows dump or an explicit dump-unavailable result before force fallback, and never kills by process name.
- **[Native input can interleave or affect the wrong desktop location]** → Serialize every raw-input sequence, revalidate PID/HWND/client bounds immediately before each step, make focus behavior explicit, cancel timed waits promptly, guarantee best-effort release before admitting the next sequence, and prefer semantic actions.
- **[Handles can outlive a map, owner, command list, or interaction]** → Include map/source fingerprints, re-resolve immediately before use, permit only one active semantic interaction, and fail stale handles without invoking the nearest current command.
- **[A debug action or mod-defined gizmo can open arbitrary UI or hide target semantics]** → Classify known native action/command/designator types, report unsupported concrete types honestly, never guess callbacks, and retain raw C# as the no-restart fallback.
- **[A large query or dragged area can freeze the main thread]** → Bound filters/results/cells, paginate by stable handle, preflight before mutation, and cap one shape at 4,096 distinct cells.
- **[Embedded transport or compiler can fail only under Unity Mono]** → Pin EmbedIO 3.5.2, `Unosquare.Swan.Lite` 3.1.0, and Mono.CSharp 4.0.0.143; package the resolved `EmbedIO.dll`, `Swan.Lite.dll`, `System.ValueTuple.dll`, and `Mono.CSharp.dll` runtime files; and require a real-game authenticated raw evaluation plus clean shutdown before runtime verification passes.
- **[Unity state is not thread-safe]** → Only immutable DTOs cross to network workers; all live state reads and mutations run through the dispatcher.
- **[Fallback assemblies cannot be unloaded]** → Report the monotonic count, cap each upload at 16 MiB, use unique compilation names, and prefer the in-process REPL for exploration. Do not impose a rate or per-run total that would force a gateway restart.
- **[Screenshot capture can allocate heavily]** → Bound dimensions/concurrency, capture at end-of-frame, destroy textures, and stream PNG bytes rather than embedding them into broad JSON state.
- **[Quickstart mutates a scenario before a late failure]** → Preflight Defs/prerequisites, use isolated save data, return a detailed mutation ledger, and design steps to be idempotent where practical.

## Migration Plan

1. Add the gateway mod and contract/client projects without adding any reference from Immersive Chefs.
2. Implement and fast-test protocol parsing, authentication, envelopes, limits, dispatcher contracts, log ring behavior, Mono.CSharp evaluator state/diagnostics, optional assembly upload, automation registry, and host fallback compilation in red/green/refactor slices.
3. Deploy only to an isolated game-data run, load Core plus the gateway, and verify manifest discovery, authenticated status, warning visibility, screenshot, input, two stateful raw-C# submissions, optional uploaded execution, shutdown, and cleanup.
4. Add a target product mod and verify `quickstart.spawn` produces a repeatable scene and evidence bundle.
5. Keep the gateway excluded from release packaging for gameplay mods. To roll back, remove/disable `fumblesneeze.rimworlddevgateway`, delete credential-free stale session metadata, and stop using its host tool; no save migration is required because the gateway persists no components into saves.

Any tool that changes a non-isolated `ModsConfig.xml` must restore the backup in `finally` and compare its post-run hash with the original before reporting success.

## Open Questions

- Which non-Windows raw-input backend, if any, should be added after the Windows development workflow is proven? This does not block the API because unsupported platforms return a capability error and retain semantic actions and uploaded execution.
- Which scenario descriptor fields should graduate into the stable `quickstart.spawn` schema after Immersive Chefs provides the first real verification cases? Unknown setup can be executed immediately through raw C# without a gateway restart.
- Should the optional assembly fallback later expose assembly identity/deduplication telemetry? Such telemetry must remain observational and must not introduce a per-run execution ceiling or restart requirement.
- Should a future API add run listing/lookup, progress polling or streaming, and remote automation cancellation? These are deliberately not part of the synchronous version-one route and require an explicit lifecycle contract rather than exposing internal registry state accidentally.
