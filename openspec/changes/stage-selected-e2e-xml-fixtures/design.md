## Context

Owner: repository tooling, `RimWorldDevGateway.EndToEndHost` at `tools/RimWorldDevGateway.EndToEndHost`.

The existing E2E and integration publishers put assemblies and manifests inside an installed owner's development-test directory. The diagnostics fixture instead needs a standalone `About`/`Defs` package for the native loader. `LocalModInstaller.Sync` replaces canonical packages and therefore cannot implement disposable fixture ownership safely.

## Goals / Non-Goals

Goals: explicit selected-group XML packages, immutable planned inventories, durable ownership before mutation, atomic visibility, preservation of existing packages, exact cleanup and retained evidence.

Non-goals: arbitrary extra mod directories, fixture assemblies or dummy projects, changing product release contents, editing Workshop, changing selection semantics, launching a game from a host test, or claiming native acceptance from filesystem checks.

## Decisions

### Explicit XML fixture manifest

`tests/Fixtures/<fixture>/fixture.json` uses the closed schema `RimWorldDevGateway/XmlFixture/v1` with `ownerPackageId`, `packageId`, `rimWorldVersion` and `packageInclude`. The source is the manifest's directory; callers cannot select an arbitrary source root. Initially includes are individual XML files: exactly `About/About.xml` plus one or more `Defs/*.xml` paths. Assembly, script, project and release payloads are outside this contract. Validate bounded JSON/XML without DTD resolution, canonical IDs, supported version, owner before fixture in the selected group, the matching About package/version and its owner dependency. Invalid Def types/values are intentional diagnostic inputs and are not semantically validated by the host.

The runner supplies candidate fixture manifest paths after selecting the owning E2E project/group. The planner filters candidates by the selected active package sequence; unselected fixtures do not require their payload files. A selected existing installed fixture ID is a conflict, not an instruction to replace it. The caller's installed-ID collection remains unchanged. Missing non-fixture dependencies remain errors in the existing runner.

Manifest and ownership-record reads are bounded to 64 KiB; each XML payload read is bounded to 8 MiB and About parsing to 1 MiB of XML characters. These are input/evidence bounds for the narrow development fixture contract. About validation consumes the same byte buffer whose hash enters the plan, so it cannot validate one read and then inventory another. Native Def semantics remain deliberately unvalidated.

### Proposed narrow host API and file boundary

- New `EndToEndXmlFixturePlanner.cs`: `PlanSelected(repositoryRoot, manifestPaths, activePackageIds, installedPackageIds, modsRoot, rimWorldVersion)` returns immutable `EndToEndXmlFixturePlan` values with owner/package/version, manifest/source/destination, exact ordered active IDs and ordinal relative-path/length/SHA-256 file inventory. An empty selection returns an empty list without filesystem writes.
- New `EndToEndXmlFixturePublisher.cs`: `Publish(plan, persistLease)` returns `EndToEndXmlFixtureLease`; the required callback persists the prepared lease through existing `EndToEndLeaseJournal` before creating any fixture transaction directory. `TryCleanup(lease, out failure)` removes only exact marker-owned transaction paths and reports refusal/failure. The serializable lease retains the canonical mods root, destination, transaction ID, owner/package/version and temporary path needed for recovery; no arbitrary cleanup target is accepted.
- New `EndToEndXmlFixtureTests.cs` in the existing host test directory, source-linked into the existing honest MCP host suite because the legacy host-test project's unconditional performance-fixture build currently requires unavailable game references.
- New `tests/Fixtures/Megamod.Diagnostics/fixture.json` registers the existing two XML files.

Existing runner, host planner/CLI, MCP project and product files are owned by their current agents. Their later integration consumes this API; this slice does not edit them.

### Selected runner integration (subsequent coordinated lease)

The reviewed selection owner has returned the runner/host metadata lease. Root adds `<RimWorldEndToEndXmlFixture Include="../Fixtures/Megamod.Diagnostics/fixture.json" />` to the marked Megamod E2E project. Host reads only unconditional literal items from the selected test's owner-matching marked project; no recursive fixture discovery or injected installed IDs. Metadata discovery and selector validation remain complete, then selected groups receive independently validated fixture plans before selected dependency availability is checked. Bundle manifests retain complete assembly metadata. Host plan JSON exposes each group's `xmlFixtures` separately.

Internal `fixture-stage` and `fixture-clean` host subcommands remain adapters behind `e2e_run_start`. Fixture staging requires one exact selected group, uses a separate per-group durable fixture lease, and occurs after product deployment immediately before its child launch. Ordinary assembly `stage` does not publish XML fixture packages. The grouped runner passes smoke's existing `-ProcessLeaseFile` and checks the retained exact child before fixture cleanup, including failed smoke output.

The typed E2E boundary allocates an exact unique owned run directory before launching the grouped runner and passes `-OwnedRunDirectory`; dry-run creates no directory. The runner writes its exact `runner-process.json` identity before fixture publication. A bounded `fixture-recovery.json` catalog (`RimWorldModdingMcp/E2EFixtureRecovery/v1`) lists only relative fixture/process lease paths and `launchAttempted`. It is atomically updated with false before fixture staging and true before invoking smoke. A killed runner cannot reliably execute finally, so the typed boundary performs bounded recovery with an independent cancellation budget after proving that exact runner has stopped. A false launch record positively proves no invocation; a true record additionally requires a valid exact child PID/start receipt proving exit. Uncertain identities/stop, path escape, ownership or catalog validation failure retain the recovery obligation and explicit cleanup failure. Recovery never scans arbitrary runs or adds a kill path; it invokes the same guarded fixture-clean adapter. Root integration/native review remains required.

### Publication and cleanup

The recovery catalog additionally records `stageProcessLeaseFile` (the same group directory's `fixture-stage-process.json`) and `stageLaunchAttempted`. The runner invokes the existing host DLL directly for fixture-stage and fixture-clean; it does not place the publisher behind a `dotnet run` child. Stage intent is flushed before process start and the exact host PID/start receipt is atomically written immediately after start. This intentionally leaves an uncertain interval if launch or receipt writing is interrupted: both normal and outer recovery fail closed. They prove publisher exit before inspecting whether a fixture lease exists, because a surviving publisher can write that lease later. The catalog's false stage intent is reserved for a synchronous in-process stage callback whose lifetime is already bounded by the recorded runner; production uses the external publisher path. Generic ProcessRunner is unchanged.

Normal runner callbacks validate bounded closed catalog/identity JSON and reject duplicate fields. Process identity checks reject reparse ancestors again at cleanup, including for the stage publisher. The final typed receipt keeps primary outcome and numeric exit code separately from cleanup status, so a failed scenario with successful recovery remains explicitly failed.

Runner exit proof precedes even absent/empty catalog handling: a surviving runner could still register publication. The production executor's nonzero exception retains its bounded structured AdapterOperationResult, so recovery reads the real exit code while rethrowing the original primary exception. If normal grouped cleanup fails after Launch returned, the cleanup exception carries that returned result to the runner catch, which writes the original streams, exit code and parseable child result together with the cleanup failure. Journal writes count serialized UTF-8 bytes against the same 64 KiB recovery limit before persisting or admitting the next publication; an existing bounded journal is left valid when rollback cannot complete.

Destination is exactly `<game>/Mods/<fixture-package-id>`. Stage on the same volume at `<game>/.rimworld-modding-mcp/xml-fixtures/<transaction-id>` outside scanned Mods. The publisher validates all destination/source ancestors against reparse points, rejects every existing destination, verifies source bytes against the immutable plan, writes its ownership marker and payload, then atomically moves the complete directory into discovery. It never backs up or removes an existing canonical package; none needs restoration because none may be replaced.

Planning canonicalizes the configured Mods root with `Path.GetFullPath` followed by `Path.TrimEndingDirectorySeparator` before deriving any plan or lease path. Recovery requires that exact canonical form and rejects a noncanonical persisted root before filesystem mutation, even with a matching ownership marker. This prevents a trailing primary or alternate separator from changing the parent used for outside-Mods staging.

Use the existing stage exception, fault-injection and lease-journal conventions. Serialize operations for the exact destination. On failure, remove only paths carrying this transaction's marker; preserve foreign/changed paths and retain the lease when cleanup is incomplete. Recovery validates recomputed paths from the lease identity and never trusts caller-supplied arbitrary directories. Marker identity, containment and reparse checks are required before deletion, including descendant entries.

Publication and cleanup serialize through an exact-destination named mutex with a bounded 30-second acquisition. The persistence callback is synchronous, non-reentrant and solely responsible for durably recording the supplied lease; a callback failure precedes fixture mutation. Cleanup preflights all leased trees before deleting any payload and removes the root marker last, retaining it across payload deletion failure. A hard process termination during an unmarked directory-creation/final-removal interval can leave an unowned empty directory: recovery refuses ambiguous ownership and reports the retained lease instead of deleting it speculatively. The normal runner owns process exclusion; this adapter is not a defense against arbitrary external filesystem mutation between OS operations.

Root integration stages only for the exact selected group, after product deployment and before child launch. It cleans any persisted fixture lease in `finally` after the exact child process has stopped, even when publication/launch/action fails. Dry-run displays planned fixture inventory separately from installed inventory and ordinary owner stages. Evidence retains fixture hashes and publication/cleanup receipts. No fixture files enter a product's artifact or release source.

### Selected expected-error accounting

An optional `expectedErrors` array extends the closed v1 manifest compatibly: omitted means none. Entries contain only `message` (exact original first line, no newline/control characters, 1–4096 characters) and `count` (integer 1–16), with at most 16 distinct messages per fixture. These development policy bounds allow small deliberate diagnostics while preventing broad suppression; the existing 64 KiB manifest bound still applies. The plan retains the manifest SHA-256 and immutable expectations. Publication rechecks that manifest hash as well as payload hashes. The internal fixture-stage adapter writes a create-new bounded 64 KiB expectation receipt beside the group lease, including selected active IDs and fixture provenance, and returns its SHA-256. Smoke accepts this file/hash only in the grouped, pre-staged E2E invocation; no public typed operation gains an ignore argument.

Both runtime and final scans use the same exact-message classification. Only native HH:mm:ss timestamp and explicit ERROR severity prefixes are removed from the matching key (unprefixed legacy errors remain supported); no context text is stripped. Full source lines, line numbers and stack/context blocks remain in retained scan evidence. Explicit native ERROR/FATAL events and the existing legacy error patterns remain failures unless exactly declared. Startup/intermediate scans reject unexpected and excess occurrences without requiring a not-yet-loaded diagnostic; final exact-process shutdown validation additionally requires every declared count. The final scan is independent of earlier snapshots, so repeated scans never consume an allowance. Warnings do not consume error expectations. Expected diagnostics remain visible for native player-workflow assertions and are never removed from Player.log.

## Risks / Trade-offs

Live-log sharing correction: the intermediate accounting call runs after the final workflow screenshot while the isolated process and its redirected stdout writer are still alive. It opens Player.log for read with `FileShare.ReadWrite`, captures the initial byte length, and reads exactly that many bytes; it neither follows a moving EOF nor retries/ignores I/O failures. BOM-aware decoding and line splitting preserve complete source lines. Only the final unterminated line is deferred in intermediate mode; evidence records `SnapshotByteLength` and `DeferredTrailingCharacters`. Final mode after exact-process shutdown opens with `FileShare.Read`, rejecting a remaining writer, reads the complete captured file and includes any unterminated final line. Missing, excess and unexpected errors are still fatal. The bound is the existing file length and the runtime's byte-array limit, not a new diagnostic-count or file-size policy.

Review clarification: receipt `activePackageIds` denotes the selected E2E metadata sequence, which excludes the implicit Gateway by the existing discovery contract. Smoke compares the actual process list against that sequence plus exactly one appended Gateway. This does not ignore arbitrary extra packages or reorder either list. The scanner selects the format from one complete snapshot: if any timestamped native header exists, all record boundaries and expected ERROR matches require timestamped headers. Untimestamped severity-looking continuation text cannot become a native record or consume an expectation. Only a legacy snapshot without timestamped headers accepts untimestamped severity headers; a legacy snapshot with no severity headers permits exact bare messages. Unexpected diagnostic detection remains active on every continuation, and retained block lines are unchanged. Native padded INFO/WARN headers delimit records without trimming message payload whitespace.

- A leftover or user-owned package with the fixture ID blocks a run → reject it and report the exact conflict; never replace it automatically.
- Termination between lease and publication → durable lease plus exact marker allows bounded recovery; missing paths are already clean.
- Source changes after planning → compare copied payload with the planned hashes before publication and fail closed on drift.
- Concurrent grouped runs → exact destination serialization and existing-destination rejection prevent overlap; the existing runner still owns game-process exclusion.
- Host tests prove filesystem ownership, not loader behavior → root must integrate the typed operation and observe reviewed native diagnostic workflows separately.

## Migration Plan

Introduce the host contracts and fixture metadata through focused RED/GREEN slices, independently review them, then integrate selected planning/publication/cleanup in the existing typed runner. No existing metadata changes meaning. Removing the opt-in fixture manifest disables future planning; existing leases still require exact cleanup. Native verification follows the coordinated Megamod part gate.
