# New mod checklist

This is the repository's default path for adding a new distributable RimWorld 1.6 mod. It keeps
package identity, OpenSpec ownership, tests, local installation, and release metadata aligned from
the first commit.

## 1. Establish identity and ownership

- Choose a stable folder name under `mods/<ModName>` and a lowercase package ID
  `fumblesneeze.<mod-designator>`. The designator must not contain the author's real name.
- Set author metadata to `Fumblesneeze` and keep the assembly/root namespace independent of the
  package ID.
- Create or extend one OpenSpec change whose owner is exactly this mod. Record observable scenarios,
  optional dependencies, research/progression, balance assumptions, and the verification tier for
  each behavior before implementation.
- Add the mod to the root `README.md` and give it a short player-facing `mods/<ModName>/README.md`.

## 2. Create the standard project layout

Start with this layout (only add folders that the mod actually needs):

```text
mods/<ModName>/
  <ModName>.csproj
  README.md
  About/About.xml                 # generated by ModSdk; do not hand-edit
  Source/
  Defs/
  Patches/Compatibility/
  Languages/English/Keyed/
  Textures/
  Release/release.json             # required for universal build/release operations
```

The project should import the pinned Zlepper ModSdk and set the repository defaults:

```xml
<Project>
  <Import Project="Sdk.props" Sdk="Zlepper.RimWorld.ModSdk" Version="0.0.9" />
  <PropertyGroup>
    <RimWorldPath>$(DefaultRimWorldPath)</RimWorldPath>
    <RimWorldManagedPath>$(RimWorldPath)\RimWorldWin64_Data\Managed</RimWorldManagedPath>
    <SteamModContentFolder>$(DefaultSteamModContentFolder)</SteamModContentFolder>
    <RimWorldModName>Example Mod</RimWorldModName>
    <RimWorldPackageId>fumblesneeze.examplemod</RimWorldPackageId>
    <RimWorldDistributionKind>Product</RimWorldDistributionKind>
    <Authors>Fumblesneeze</Authors>
    <AssemblyName>ExampleMod</AssemblyName>
    <RootNamespace>ExampleMod</RootNamespace>
    <IncludeHarmony>true</IncludeHarmony>
    <OutputFolder>$(ArtifactsRoot)Mods</OutputFolder>
    <Description>Short player-facing description.</Description>
  </PropertyGroup>
  <Import Project="Sdk.targets" Sdk="Zlepper.RimWorld.ModSdk" Version="0.0.9" />
</Project>
```

`About/About.xml` is emitted from the project metadata. Do not copy Workshop assemblies, Harmony,
the Gateway, test assemblies, symbols, or build caches into a product package. Keep static Defs and
conditional PatchOperations in XML; put lifecycle/computed behavior in a narrow C# adapter.

## 3. Define the release profile early

Create `Release/release.json` before the first package build. It must use schema
`RimWorldModRelease/v1`, point to the exact project and package source, declare the positive
`packageInclude` allowlist, supported RimWorld build, Workshop dependencies/DLC separately, player
description/preview, and verification profile. A new unpublished item is explicitly `Private` with
`allowFirstPublication: true`; later updates set the committed Workshop ID and disable first
publication. Keep change notes player-facing and specific.

Run profile validation before a build:

```powershell
$mcp = '.\tools\RimWorldModding.Mcp\RimWorldModding.Mcp.csproj'
dotnet run --project $mcp -- tool call release_profile_validate `
  --arguments '{"packageId":"fumblesneeze.examplemod"}' -o json
```

## 4. Add the honest test layers

- Put pure rules/statistics in `<Mod>.Unit`; keep it free of loaded mods, Harmony, and populated
  game Def databases.
- Put an explicitly owned Harmony patch in `<Mod>.Harmony`, with guaranteed removal.
- Put lightweight real `Verse.Def` fixtures in `<Mod>.Defs` when a host test needs a scoped Def DB.
- Put finalized XML, real Core/Workshop Defs, full optional-mod initialization, rendering, jobs, and
  PatchOperations in an isolated in-game integration project.
- Put multi-frame native player workflows in a separately marked E2E project. Declare the complete
  exact active package order (Gateway is appended only by the runner).

Use focused TDD red/green/refactor for each behavior, then run the smallest owning test selection.
Read `docs/TestingEnvironments.md` before deciding whether a test needs a fresh RimWorld process.

For a registered host-test suite, the typed operation keeps the selection explicit and rejects a
zero-test result:

```powershell
$mcp = '.\tools\RimWorldModding.Mcp\RimWorldModding.Mcp.csproj'
dotnet run --project $mcp -- tool call test_run `
  --arguments '{"suite":"ExampleMod.Unit","filter":null,"configuration":"Release"}' -o json
```

## 5. Build and install using the default path

The canonical loop is:

```powershell
$mcp = '.\tools\RimWorldModding.Mcp\RimWorldModding.Mcp.csproj'
dotnet run --project $mcp -- tool call mod_build `
  --arguments '{"packageId":"fumblesneeze.examplemod","configuration":"Release","modsRoot":null}' -o json
```

If the package is already built and only needs to be copied into the local game, use the explicit
install-only operation:

```powershell
dotnet run --project $mcp -- tool call local_mod_sync `
  --arguments '{"packageId":"fumblesneeze.examplemod","modsRoot":null}' -o json
```

`mod_build` builds first and installs only when the build succeeds. It copies the profile's exact
allowlist into the local `Mods/<package-id>` directory, stages outside the scanned Mods folder on
the install volume, and retains no install backup. `local_mod_sync` repeats only the install step
for an already-built package. Use `package_validate` to inspect the exact manifest and hashes.

Never deploy to Steam Workshop content. Never use a retained install backup as a second mod copy;
rebuild the repository package if an older local build is needed. Subscriber release verification is
the one separate workflow that temporarily moves the local package so the subscribed copy can be
tested and then restored.

## 6. Verify and release

After focused tests and package validation:

1. Run independent code review and resolve findings.
2. Build the reviewed Release package and inspect its allowlist, About metadata, Defs, patches,
   localization, and assets.
3. Run the exact isolated in-game integration/E2E workflow with developer mode, inspect the live
   player-visible result, and review the complete `Player.log` for errors and warnings.
4. Mark OpenSpec tasks only when their evidence exists.
5. Use `release_prepare`, personally review its immutable plan, then use `release_publish` only for
   the explicitly authorized Steam mutation. First publication is private; verify the subscribed
   copy before promotion.

Keep all run evidence under ignored `artifacts/`, keep downloaded Workshop content read-only, and
never commit tokens, saves, live Gateway manifests, generated packages, or test output.
